## Заметки

1. Спросить у менеджеров есть ли фигма на проект о постах

2. почему после замены base branch появился лишний коммит в ПР

   **Коротко:** PR пересчитался относительно новой базы `X`, а история `Z` всё ещё содержит старые коммиты из `Y` — Git (и Arcanum) не считает их «уже в `X`», если мерж был не обычным merge.

   ### Что произошло по шагам

   ```
   X ─────────────────────────────► (после merge PR #1)
        \
         Y ──► merge в X
          \
           Z ── PR был Z→Y, стал Z→X
   ```

   После мержа `Y → X` Arcanum переназначил второй PR на `X` — это нормально: база `Y` «исчерпана», целевая ветка для фичи теперь `X`.

   ### Почему в PR #2 виден коммит из `Y`

   PR показывает коммиты, которые есть в `Z`, но **не считаются частью истории `X`**.

   #### 1. Squash merge (самый частый случай)

   Если `Y → X` смержили **squash**-ом:
   - в `X` появился **один новый** коммит `S` с содержимым `Y`;
   - в `Z` остались **оригинальные** коммиты `y1, y2, ...` с **другими SHA**;
   - для Git это **разные коммиты**, хотя diff может совпадать.

   Поэтому в PR `Z → X` коммиты из `Y` снова попадают в список — они не предки `X`, только предки `Z`.

   #### 2. Обычный merge (без squash)

   Если был **merge commit** и коммиты из `Y` вошли в `X` как есть:
   - коммиты `Y` должны быть предками `X`;
   - в PR `Z → X` обычно остаются **только коммиты, сделанные уже в `Z`**.

   Если они всё равно видны — часто `X` ещё не содержит merge (PR только смержен, ветка не подтянута) или merge прошёл иначе (rebase, cherry-pick).

   #### 3. Коммиты vs diff

   Иногда во вкладке **Commits** лишние коммиты есть, а во **Files changed** — почти ничего лишнего: изменения из `Y` уже в `X`, diff пустой или минимальный. Это как раз типично для squash + retarget.

   ### Что делать с `Z`

   **Если diff лишний (дублирует `Y`):**

   ```bash
   arc checkout Z
   arc rebase X   # или merge X в Z
   arc push
   ```

   После rebase на актуальный `X` в PR останутся только коммиты, уникальные для `Z`.

   **Если diff пустой** — PR можно закрыть: всё уже в `X`.

   ### Как избежать в следующий раз
   1. После мержа `Y → X` сразу **rebase `Z` на `X`**, а не ждать автопереназначения PR.
   2. Уточнить политику merge в репо: при **squash** дочерние ветки почти всегда «тащат» старые SHA.
   3. Для цепочки фич иногда удобнее: `Z` от `X`, cherry-pick только нужных коммитов, или один PR с последовательными коммитами.

   **Итог:** коммит из `Y` появился не потому что его «нет в `X`» по смыслу, а потому что **история `Z` всё ещё ссылается на старые коммиты `Y`**, а после squash/rebase они не совпадают с тем, что лежит в `X`. PR показывает разницу **историй**, а не только **содержимого**.
