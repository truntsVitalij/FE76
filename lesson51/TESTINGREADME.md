# Тестирование ПО: виды, уровни, подходы, TDD

Материал для занятия: зачем тестировать, какие бывают тесты и как устроен подход **TDD**.

> **Одной фразой:** тест — это **автоматическая или ручная проверка**, что код ведёт себя как ожидается. Пирамида: много быстрых **unit**, меньше **integration**, ещё меньше **e2e**. **TDD** — сначала красный тест, потом минимальный код, потом рефакторинг.

## зеленые тесты - всё тесты прошли без ошибок (PASSED)

## красные тесты - есть хотя бы один упавший тест (FAILED)

## покрытие тестами (test coverage) - отношения кол-ва строк кода тестов к строкам кода.

## Зачем тестировать

| Зачем                  | Пояснение                                        |
| ---------------------- | ------------------------------------------------ |
| Ловить баги раньше     | Дешевле чинить до продакшена                     |
| Документация поведения | Тест показывает, _как_ должен работать код       |
| Смелость рефакторить   | Есть страховка: сломал — тесты красные           |
| Регрессии              | Старый баг не возвращается незаметно             |
| Дизайн API             | При TDD API модуля получается удобнее для вызова |

Тесты **не заменяют** code review и не гарантируют отсутствие багов на 100%. Они снижают риск и ускоряют изменения.

## Ручное vs автоматизированное

|        | Ручное (manual)                        | Автоматизированное (automated) (авто-тесты) |
| ------ | -------------------------------------- | ------------------------------------------- |
| Кто    | Человек кликает / проверяет            | Скрипт / CI                                 |
| Плюсы  | Гибко, ловит UX-странности             | Повторяемо, быстро на регрессии             |
| Минусы | Дорого, медленно, зависит от внимания  | Писать и поддерживать дорого                |
| Когда  | Exploratory, новый UI, редкие сценарии | Unit, критичные флоу, CI на каждый PR       |

На практике: **автотесты на стабильную логику** + **ручной/exploratory** на новый UI и edge-кейсы.

## Пирамида тестирования

```
            /\
           /  \        E2E / UI
          /----\       мало, медленные, хрупкие
         /      \
        /--------\     Integration
       /          \    среднее кол-во
      /------------\
     /              \  Unit
    /________________\ много, быстрые, дешёвые
```

| Уровень     | Сколько | Скорость | Стоимость поддержки |
| ----------- | ------- | -------- | ------------------- |
| Unit        | Много   | Быстро   | Низкая              |
| Integration | Средне  | Средне   | Средняя             |
| E2E         | Мало    | Медленно | Высокая             |

Анти-паттерн — **перевёрнутая пирамида**: почти только e2e. Долго бегут, часто флапают, сложно дебажить.

## Уровни тестов

### Unit (модульные)

Проверяют **одну функцию / класс / хук** в изоляции.

```ts
// пример идеи
expect(sum(2, 3)).toBe(5);
expect(generateCodeVerifier()).toHaveLength(64);
```

- Внешние зависимости (API, БД) **мокают**.
- Самые быстрые и стабильные.

### Integration (интеграционные)

Проверяют **несколько частей вместе**: компонент + хук + контекст, модуль + API-клиент (с моком HTTP), несколько сервисов.

Пример: `SignIn` рендерится → клик → вызывается `redirectToSpotifyAuth` (замоканный `location`).

### E2E (end-to-end)

Полный сценарий **как пользователь**: браузер → UI → реальный (или staging) backend.

Пример: открыть приложение → Sign in → увидеть библиотеку плейлистов.

|                     | Unit    | Integration | E2E     |
| ------------------- | ------- | ----------- | ------- |
| Изоляция            | Высокая | Средняя     | Низкая  |
| Реализм             | Низкий  | Средний     | Высокий |
| Где падает — искать | Легко   | Средне      | Сложнее |

### Другие «уровни / срезы»

| Название                 | Смысл                                               |
| ------------------------ | --------------------------------------------------- |
| **Smoke**                | «Приложение вообще стартует?» минимальный набор     |
| **Sanity**               | Быстрая проверка после мелкого фикса                |
| **Regression**           | Что старое не сломалось                             |
| **Acceptance / UAT**     | Заказчик / продукт принимает фичу                   |
| **Component** (в фронте) | Тест UI-компонента (часто ближе к unit/integration) |

## Типы по цели / виду

### По объекту

| Тип                | Что проверяем                             |
| ------------------ | ----------------------------------------- |
| **Unit**           | Функции, утилиты, редюсеры                |
| **API / Contract** | HTTP-контракт, статус-коды, схема JSON    |
| **UI / Component** | Рендер, клики, доступность                |
| **E2E**            | Пользовательский сценарий целиком         |
| **Visual**         | Скриншоты / пиксельное сравнение          |
| **Snapshot**       | Сериализованный вывод «как в прошлый раз» |

### По времени в процессе

| Тип                         | Когда                             |
| --------------------------- | --------------------------------- |
| **Alpha / Beta**            | Внутреннее / внешнее предрелизное |
| **Pre-production**          | На staging перед продом           |
| **Production / monitoring** | Синтетические проверки в проде    |

### По характеру изменений

| Тип              | Смысл                           |
| ---------------- | ------------------------------- |
| **Smoke**        | Критичный минимум «жив ли билд» |
| **Regression**   | Не сломали старое               |
| **Confirmation** | Баг-фикс действительно починен  |

## Методы: black / white / gray box

| Метод         | Знание кода       | Как тестируют                  |
| ------------- | ----------------- | ------------------------------ |
| **Black box** | Не смотрят внутрь | Вход → выход, по требованиям   |
| **White box** | Знают реализацию  | Покрывают ветки, условия, пути |
| **Gray box**  | Частично знают    | API + понимание архитектуры    |

На фронте: e2e чаще black box; unit — white box; integration с моками API — gray box.

## Функциональное vs нефункциональное

### Функциональное

«Делает ли система то, что должна?»

- Логин работает
- Кнопка создаёт плейлист
- Форма валидирует email

### Нефункциональное (качество)

| Тип                      | Вопрос                               |
| ------------------------ | ------------------------------------ |
| **Performance**          | Насколько быстро? нагрузка?          |
| **Load / Stress**        | Как под нагрузкой / за пределом?     |
| **Security**             | XSS, утечки токенов, auth bypass?    |
| **Usability**            | Удобно ли пользоваться?              |
| **Accessibility (a11y)** | Клавиатура, screen reader, контраст? |
| **Compatibility**        | Браузеры, устройства?                |
| **Reliability**          | Падения, восстановление?             |

Для FE-курса обычно фокус: **unit + component + немного e2e**; a11y и perf — по возможности.

## Тестирование на фронтенде

| Что                      | Пример                  | Инструменты              |
| ------------------------ | ----------------------- | ------------------------ |
| Утилиты / PKCE / парсеры | `generateCodeChallenge` | Vitest / Jest            |
| Редюсеры, селекторы      | Redux slice             | Vitest                   |
| Хуки                     | `useAccessToken`        | `renderHook` (RTL)       |
| Компоненты               | Button, SignIn          | React Testing Library    |
| Страницы + роутинг       | клик → navigate         | RTL + MemoryRouter       |
| Браузерный сценарий      | логин Spotify (mock)    | Playwright / Cypress     |
| Визуал                   | отступы, тема           | Chromatic / Percy (опц.) |

### Что тестировать в React (практика RTL)

Предпочтение: **поведение для пользователя**, не детали реализации.

```ts
// ✅ хорошо: что видит пользователь
expect(screen.getByRole("button", { name: /sign in/i })).toBeInTheDocument();

// ❌ хрупко: внутренние className / state
expect(wrapper.find(".pageContainer")).toHaveLength(1);
```

Правило RTL: _«The more your tests resemble the way your software is used, the more confidence they give you.»_

### Snapshot — осторожно

- Плюс: быстро поймать случайный дифф UI-дерева.
- Минус: огромные снапшоты, «approve all» без чтения → ложное чувство безопасности.
- Лучше sparingly, для стабильных чистых компонентов.

## Структура теста (AAA / Given–When–Then)

**AAA** — самый частый шаблон:

```ts
it("sums two numbers", () => {
  // Arrange — подготовка
  const a = 2;
  const b = 3;

  // Act — действие
  const result = sum(a, b);

  // Assert — проверка
  expect(result).toBe(5);
});
```

**Given–When–Then** (из BDD) — то же по смыслу:

| AAA     | GWT          |
| ------- | ------------ |
| Arrange | Given (дано) |
| Act     | When (когда) |
| Assert  | Then (тогда) |

Один тест — **одна идея** (одно поведение). Имя теста читается как спецификация:

```ts
it('returns null when access_token is missing', ...)
it('redirects to /home when token exists', ...)
```

## Моки, стабы, фейки, шпионы

| Термин    | Смысл                                 | Пример                          |
| --------- | ------------------------------------- | ------------------------------- |
| **Stub**  | Заглушка с готовым ответом            | `getUser` всегда `{ id: 1 }`    |
| **Mock**  | Объект с ожиданиями вызовов           | «должен вызваться 1 раз с id=5» |
| **Spy**   | Следит за реальным/частичным методом  | `vi.spyOn(api, 'fetch')`        |
| **Fake**  | Упрощённая рабочая реализация         | In-memory fake store            |
| **Dummy** | Нужен только чтобы заполнить аргумент | пустой callback                 |

На фронте часто:

```ts
vi.stubGlobal(
  "fetch",
  vi.fn().mockResolvedValue({
    ok: true,
    json: async () => ({ access_token: "test" }),
  }),
);
```

Мокайте **границы** (сеть, `localStorage`, `location`), не всю внутренность приложения.

## Гайд: подключение Cypress

**Cypress** — инструмент **e2e** (и component) тестов с удобным UI: открывает браузер, кликает как пользователь, показывает шаги и DOM.

Подходит, когда нужно проверить сценарий целиком: открыл страницу → нажал кнопку → увидел текст / ушёл на другой URL.

> Ниже — подключение к Vite + React проекту вроде `diplom` (`http://127.0.0.1:8888`).

### 1. Установка

Из корня фронтенд-проекта:

```bash
npm install -D cypress
```

Опционально (удобно в CI: поднять dev-server и дождаться порта):

```bash
npm install -D start-server-and-test
```

### 2. Первый запуск (создание структуры)

```bash
npx cypress open
```

Cypress предложит **E2E Testing** → выбрать браузер (Chrome) → создаст папки и конфиг.

Типичная структура:

```text
project/
├── cypress/
│   ├── e2e/                 # ваши *.cy.ts тесты
│   ├── fixtures/            # JSON-заглушки ответов API
│   └── support/
│       ├── e2e.ts           # подключается перед каждым тестом
│       └── commands.ts      # кастомные команды cy.login() и т.п.
├── cypress.config.ts
└── package.json
```

### 3. Конфиг `cypress.config.ts`

Для `diplom` (порт **8888**, host **127.0.0.1**):

```ts
import { defineConfig } from "cypress";

export default defineConfig({
  e2e: {
    baseUrl: "http://127.0.0.1:8888",
    specPattern: "cypress/e2e/**/*.cy.{js,jsx,ts,tsx}",
    supportFile: "cypress/support/e2e.ts",
    video: false, // в учёбе часто выключают; в CI можно включить
    screenshotOnRunFailure: true,
    // setupNodeEvents(on, config) {},
  },
});
```

`baseUrl` позволяет писать `cy.visit('/sign-in')` вместо полного URL.

### 4. Скрипты в `package.json`

```json
{
  "scripts": {
    "dev": "vite",
    "cy:open": "cypress open",
    "cy:run": "cypress run",
    "test:e2e": "start-server-and-test dev http://127.0.0.1:8888 cy:run"
  }
}
```

| Команда            | Зачем                                           |
| ------------------ | ----------------------------------------------- |
| `npm run cy:open`  | UI-режим (удобно писать тесты)                  |
| `npm run cy:run`   | Headless (для CI)                               |
| `npm run test:e2e` | Поднять Vite → дождаться URL → прогнать Cypress |

**Важно:** перед `cy:open` / `cy:run` приложение должно быть запущено (`npm run dev`), либо используйте `test:e2e`.

### 5. TypeScript (если проект на TS)

Обычно достаточно:

```bash
npm install -D typescript
```

В `cypress/tsconfig.json` (можно отдельно от корневого):

```json
{
  "compilerOptions": {
    "target": "ES2020",
    "lib": ["ES2020", "DOM"],
    "types": ["cypress"],
    "isolatedModules": false
  },
  "include": ["**/*.ts"]
}
```

Имена файлов тестов: `something.cy.ts`.

### 6. Первый e2e-тест

`cypress/e2e/sign-in.cy.ts`:

```ts
describe("Sign in page", () => {
  beforeEach(() => {
    cy.visit("/sign-in");
  });

  it("shows title and Sign in button", () => {
    cy.contains("Spotify Music").should("be.visible");
    cy.contains("button", /sign in/i).should("be.visible");
  });

  it("redirects to /home when access_token exists", () => {
    window.localStorage.setItem("access_token", "test-token");
    cy.visit("/sign-in");
    cy.location("pathname").should("eq", "/home");
  });
});
```

Запуск:

```bash
# терминал 1
npm run dev

# терминал 2
npm run cy:open
```

Выберите спек `sign-in.cy.ts` и смотрите прогон в UI.

### 7. Базовые команды Cypress

| Команда                    | Смысл                            |
| -------------------------- | -------------------------------- |
| `cy.visit('/path')`        | Открыть страницу                 |
| `cy.get('selector')`       | Найти элемент (CSS)              |
| `cy.contains('text')`      | Найти по тексту                  |
| `cy.click()` / `cy.type()` | Действия                         |
| `cy.should('be.visible')`  | Assertion (retry автоматически)  |
| `cy.intercept(...)`        | Перехватить / замокать HTTP      |
| `cy.wait('@alias')`        | Дождаться перехваченного запроса |
| `cy.location('pathname')`  | Проверить URL                    |
| `cy.screenshot()`          | Скриншот                         |

> Cypress **ретраит** проверки сам — меньше ручных `wait(1000)`. Избегайте фиксированных `cy.wait(3000)` без нужды.

### 8. Мок API через `cy.intercept`

Не ходите в реальный Spotify из e2e без подготовки — мокайте:

```ts
it("loads playlists on home", () => {
  cy.intercept("GET", "https://api.spotify.com/v1/me/playlists*", {
    statusCode: 200,
    body: {
      items: [{ id: "1", name: "My Playlist" }],
    },
  }).as("playlists");

  window.localStorage.setItem("access_token", "test-token");
  cy.visit("/home");
  cy.wait("@playlists");
  cy.contains("My Playlist"); // когда UI начнёт рендерить список
});
```

Фикстуры:

```ts
// cypress/fixtures/me.json — заранее сохранить ответ
cy.intercept("GET", "**/v1/me", { fixture: "me.json" }).as("me");
```

### 9. Кастомные команды

`cypress/support/commands.ts`:

```ts
Cypress.Commands.add("loginByToken", (token = "test-token") => {
  window.localStorage.setItem("access_token", token);
});

declare global {
  namespace Cypress {
    interface Chainable {
      loginByToken(token?: string): Chainable<void>;
    }
  }
}

export {};
```

В `cypress/support/e2e.ts` должен быть импорт:

```ts
import "./commands";
```

В тесте:

```ts
cy.loginByToken();
cy.visit("/home");
```

### 10. Селекторы: как искать элементы устойчиво

| Подход                         | Пример                             | Комментарий           |
| ------------------------------ | ---------------------------------- | --------------------- |
| По роли/тексту                 | `cy.contains('button', 'Sign in')` | Ближе к пользователю  |
| `data-cy`                      | `cy.get('[data-cy=sign-in]')`      | Стабильно для e2e     |
| Длинные CSS/классы CSS-modules | `.sign-in_pageContainer_xyz`       | Хрупко, лучше не надо |

В разметке:

```tsx
<button data-cy="sign-in" onClick={handleSignIn}>
  Sign in
</button>
```

### 11. Cypress Component Testing (кратко)

Кроме e2e, Cypress умеет **component tests** (изолированный компонент в браузере). Для React + Vite:

```bash
npx cypress open
# выбрать Component Testing → Vite + React
```

На курсе достаточно начать с **e2e**. Component — опционально рядом с RTL.

### 12. CI (headless)

```bash
npm run test:e2e
# или
npx cypress run --browser chrome
```

В GitHub Actions идея: `npm ci` → `start-server-and-test` → `cypress run`. Артефакты: скриншоты при падении.

### 13. Типичные проблемы при подключении

| Проблема                         | Что сделать                                                                   |
| -------------------------------- | ----------------------------------------------------------------------------- |
| `cy.visit` connection refused    | Не запущен `npm run dev` / неверный `baseUrl` / порт                          |
| Тест видит пустой экран          | Роут другой (`/sign-in`), ошибка в консоли React                              |
| Flaky «element not found»        | Дождаться появления: `cy.contains(...).should('be.visible')`; не `wait(5000)` |
| CORS / чужой API                 | `cy.intercept` на ответы                                                      |
| OAuth Spotify в e2e              | Не гонять реальный логин в CI; мок token в `localStorage` + intercept API     |
| `baseUrl` localhost vs 127.0.0.1 | Должен совпадать с Vite `server.host` (у `diplom` — `127.0.0.1`)              |

### 14. Чеклист подключения Cypress

```text
# 1. npm i -D cypress
# 2. npx cypress open → создать e2e
# 3. baseUrl = URL Vite-приложения
# 4. scripts: cy:open, cy:run, (test:e2e)
# 5. Первый тест: visit + contains
# 6. API — через cy.intercept / fixtures
# 7. data-cy на ключевые кнопки
# 8. В CI — cypress run + поднятый dev/preview
```

### Cypress vs Playwright (чтобы выбрать)

|                | Cypress                                        | Playwright                           |
| -------------- | ---------------------------------------------- | ------------------------------------ |
| DX / UI раннер | Очень удобный                                  | Хороший, другой UX                   |
| Браузеры       | Chrome-family отлично; ограничения исторически | Chromium, Firefox, WebKit из коробки |
| Параллельность | Через Dashboard / настройки                    | Сильная из коробки                   |
| Для учёбы      | Часто проще начать                             | Чуть «инженернее», тоже ок           |

Оба закрывают e2e. На занятии достаточно освоить **один**.

## TDD — Test-Driven Development

**TDD** — практика разработки, при которой **тесты пишут до продакшен-кода**.

Не «тесты после фичи», а цикл:

```
Красный → Зелёный → Рефакторинг → (повторить)
```

Идея Кента Бека / Extreme Programming: тест задаёт желаемое поведение, код догоняет тест.

---

## Принципы и цикл TDD

### Три закона TDD (Uncle Bob / Robert C. Martin)

1. **Нельзя писать прод-код**, пока не написан падающий unit-тест.
2. **Нельзя писать теста больше**, чем нужно, чтобы упасть (компиляция/assert).
3. **Нельзя писать прод-кода больше**, чем нужно, чтобы пройти текущий тест.

Следствие: маленькие шаги, частая обратная связь.

### Цикл Red → Green → Refactor

```
1. RED     Написать тест на новое поведение → тест ПАДАЕТ
2. GREEN   Написать минимальный код, чтобы тест прошёл
3. REFACTOR Улучшить дизайн, тесты остаются зелёными
4.         Следующее поведение → снова RED
```

| Фаза         | Цель                                    | Чего избегать                     |
| ------------ | --------------------------------------- | --------------------------------- |
| **Red**      | Зафиксировать требование тестом         | Писать сразу большой код          |
| **Green**    | Заставить пройти самым простым способом | Идеальный дизайн «сразу»          |
| **Refactor** | Убрать дубли, улучшить имена/структуру  | Ломать поведение (тесты страхуют) |

### Принципы хорошего TDD

| Принцип                    | Смысл                                     |
| -------------------------- | ----------------------------------------- |
| **Маленькие шаги**         | Один аспект поведения за цикл             |
| **Тест как спецификация**  | Имя и assert описывают «что», не «как»    |
| **Быстрая обратная связь** | Unit-тесты секунды, не минуты             |
| **Изоляция**               | Unit не ходит в сеть/БД                   |
| **FIRST**                  | см. ниже                                  |
| **Дизайн через тесты**     | Сложно тестировать → сигнал упростить API |

### FIRST (качества хороших unit-тестов)

|                            |                                       |     |
| -------------------------- | ------------------------------------- | --- |
| **F**ast                   | Быстрые                               |     |
| **I**solated / Independent | Не зависят друг от друга              |     |
| **R**epeatable             | Одинаковый результат всегда           |     |
| **S**elf-validating        | Pass/fail без ручной проверки глазами |     |
| **T**imely                 | Написаны вовремя (в TDD — до кода)    |     |

### Что TDD _не_ обещает

- Не заменяет e2e и ручной UX-тест.
- Не равен «100% coverage любой ценой».
- Coverage — метрика, не цель: можно покрыть бессмысленными тестами.

## TDD на практике (пример)

Задача: функция `normalizeToken` — пустая / `"undefined"` → `null`, иначе строка.

### 1. RED

```ts
import { describe, it, expect } from "vitest";
import { normalizeToken } from "./normalize-token";

describe("normalizeToken", () => {
  it("returns null for empty value", () => {
    expect(normalizeToken(null)).toBeNull();
    expect(normalizeToken("")).toBeNull();
  });
});
```

Тест падает — функции ещё нет.

### 2. GREEN

```ts
export function normalizeToken(value: string | null): string | null {
  if (!value) return null;
  return value;
}
```

### 3. RED снова (новое поведение)

```ts
it('returns null for string "undefined"', () => {
  expect(normalizeToken("undefined")).toBeNull();
});
```

### 4. GREEN

```ts
export function normalizeToken(value: string | null): string | null {
  if (!value || value === "undefined") return null;
  return value;
}
```

### 5. REFACTOR

Имена, вынос константы, без изменения поведения — тесты зелёные.

Так же TDD применяют к утилитам PKCE, редюсерам, чистым функциям валидации.

---

## Когда TDD помогает / когда нет

### Помогает

- Чистая логика, утилиты, алгоритмы
- Редюсеры, парсеры, форматтеры
- Баги: сначала тест, воспроизводящий баг → потом фикс (bug-driven)
- Команда договорилась о стиле API

### Сложнее / осторожно

- Ранний UI-эксперимент («набросать макет»)
- Сильная зависимость от внешнего API без контракта
- Визуальный дизайн «на глаз»
- Легаси без швов для изоляции (сначала characterization tests)

Прагматичный подход: **TDD для доменной логики**, для UI — тесты рядом с поведением (часто после первого наброска или сразу на критичные флоу).

---

## Связанные подходы: BDD, ATDD

| Подход                    | Фокус                                                                  |
| ------------------------- | ---------------------------------------------------------------------- |
| **TDD**                   | Разработчик, unit-уровень, дизайн кода                                 |
| **BDD** (Behavior-Driven) | Поведение системы языком бизнеса (`Given/When/Then`, Cucumber/Gherkin) |
| **ATDD** (Acceptance)     | Acceptance-критерии до реализации, часто вместе с QA/PO                |

BDD не противоречит TDD: TDD внутри, BDD — на уровне фич/сценариев.

Пример Gherkin:

```gherkin
Given пользователь не авторизован
When он открывает /home
Then его перенаправляет на /sign-in
```

## Хорошие практики

1. Тесты **детерминированы** (без `Math.random` / времени без контроля).
2. Не тестируйте **приватные детали** — только публичное поведение.
3. Не дублируйте прод-логику в тесте (иначе оба сломаются одинаково).
4. Падающий тест должен **понятно объяснять**, что сломано.
5. Держите unit-тесты в CI на каждый PR.
6. Мокайте сеть через **MSW** или `vi.fn`, не через хрупкие реализации.
7. Флакающие e2e — чините или удаляйте; флаки убивают доверие к CI.
8. Покрытие: смотрите **непокрытые критичные ветки**, не гонитесь за 100%.

## Типичные ошибки

| Ошибка                                                         | Почему плохо                                  |
| -------------------------------------------------------------- | --------------------------------------------- |
| Только e2e                                                     | Медленно, хрупко, дорого                      |
| Тесты реализации (`useState` раз)                              | Ломаются при рефакторинге без смены поведения |
| Один огромный тест на всё                                      | Непонятно, что упало                          |
| `access_token = undefined` в LS и «зелёные» тесты без проверки | Ложное спокойствие                            |
| Snapshot на всё подряд                                         | Шум, approve вслепую                          |
| Зависимость тестов друг от друга (порядок)                     | Флаки                                         |
| Писать тесты «для coverage»                                    | Мёртвый код проверок                          |

## Чеклист

```text
# 1. Знать пирамиду: unit > integration > e2e
# 2. Различать functional / non-functional, manual / automated
# 3. Black / white / gray box — разные углы зрения
# 4. AAA: Arrange → Act → Assert
# 5. Моки на границах (fetch, storage), не внутри всей логики
# 6. RTL: тестировать как пользователь (roles, text)
# 7. TDD: Red → Green → Refactor
# 8. Три закона TDD: сначала падающий тест, минимум кода
# 9. FIRST: Fast, Isolated, Repeatable, Self-validating, Timely
# 10. TDD идеален для чистой логики; UI — прагматично
# 11. Flaky tests чинить / убирать
# 12. Coverage — индикатор, не цель
# 13. Cypress: baseUrl = Vite URL, cy:open / cy:run, API через intercept
```

Мини-шпаргалка цикла TDD:

```text
напиши падающий тест
    → напиши чуть кода (зелёный)
        → отрефактори
            → следующий тест
```
